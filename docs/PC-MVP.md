## 현재: 1.0.5 — 검색 속도·켤 때 따라잡기·띄어쓰기·오탈자 (2026-10-26)

### 완료

**1단계 — 파일 이름 검색**
- 검색 위치·제외 폴더 선택, 파일명·폴더명·경로 색인과 검색, 파일 열기·폴더에서 보기
- 폴더 감시(`fs.watch`)로 신규·수정·삭제 자동 반영, 변경분은 `findinside-delta.json`

**2단계 — 문서 내용 검색** (ADR-0001, ADR-0002)
- SQLite FTS5 + 한국어 2글자 단위 토큰, 한 글자 색인, OCR 모음 혼동 색인
- TXT·CSV·PDF·DOCX·XLSX·PPTX·HWP·HWPX 추출, 쪽·표·셀·슬라이드 위치
- 검색·추출을 worker로 분리해 입력 멈춤과 한/영 전환 막힘 해결

**3단계 — 이미지 속 글자**
- Windows.Media.Ocr 상주 프로세스, 2배 확대, 세로쓰기 다시 읽기, 낮은 우선순위
- 한자 한글음(Unihan kHangul) 검색

**4단계 — 메일** (ADR-0004)
- MSG·EML 파일과 첨부(3단계 깊이까지)
- IMAP(imapflow)·POP3(직접 구현) 계정, 비밀번호는 DPAPI 암호화
- 메일 탭, 편지함 선택, 묶음을 먼저 받고 해석(연결 끊김 방지), 끊기면 다시 접속

**5단계 — 검색 화면 다듬기**
- 분류 탭, 정렬(관련도·최신순), 날짜 표시, 검색 중·실패·색인 진행 안내

**6단계 — 판매 준비**

**1.0.5 (2026-10-26 배포 — GitHub 릴리스 v1.0.5, 스토어는 제출 대기)** — "켤 때마다 색인하나?", "에브리띵처럼 빨라야", "띄어쓰기·오탈자도 찾아야"
- **켤 때 따라잡기** (`indexer.js` `catchUp`): 전에는 켤 때 저장된 이름 목록을 그대로 써서, 앱이 꺼져 있던 동안 생긴 파일은 "다시 색인"을 누를 때까지 안 나왔다. 이제 폴더마다 수정 시각만 확인하고(NTFS는 폴더 안에서 파일이 생기거나 지워지거나 이름이 바뀌면 폴더 시각이 바뀐다), 바뀐 폴더만 다시 읽는다. 실측(C:\·D:\ 66만 개): 0.4~2초. 폴더 시각은 색인 파일의 폴더 항목 `mtime`에 적는다(형식 2). 1.0.4까지의 옛 목록은 첫 따라잡기 때 감시 대상 폴더를 모두 다시 읽어(2초) 시각을 적고, 그 뒤로는 시각만 본다 — 전체를 다시 만들지 않는다. 에브리띵은 NTFS 변경 기록(USN 저널)을 읽지만 관리자 권한이 필요해 이 방식을 택했다. 폴더 감시가 폴더만 지우고 남긴 안쪽 항목도 이때 정리한다
- Temp·AppData·Windows 같은 늘 바뀌는 폴더(`CHURN_PATH`)는 감시·따라잡기에서 뺀다(전과 같음). 단 사용자가 그런 곳(예: `D:\tmp\자료`)을 검색 위치로 직접 골랐으면 그 안은 뺀다고 보지 않는다 (`isChurn`)
- **전체 색인 4~6배 빠르게**: 폴더를 하나씩 읽던 것을 16개씩 동시에 읽는다. C:\ 74만 개 101초 → 16~23초
- **이름 결과 먼저**: 전에는 파일 내용 검색(내용 DB 8.7GB, 디스크에서 처음 읽을 때 2~5초)이 끝나야 결과가 한꺼번에 떴다. 이제 화면이 이름만 먼저 찾아(0.1~0.3초) 그리고, 내용 결과가 오면 바꾼다("파일 내용에서도 찾는 중…"). 내용 검색은 따로 띄운 `contentSearchWorker.js`가 하고, 그동안 새 검색어가 오면 아직 시작 안 한 이전 요청은 버린다 (줄 서서 다 돌면 마지막 검색이 한참 늦었다)
- **내용 검색 자체를 빠르게** (사용자 화면에서 "ai 질의 유형" 14초 넘게 "검색 중"): 맞는 조각 번호는 FTS 색인에서 0.1초 안에 나오는데, 조각마다 본문 행(8.7GB)을 읽어 파일을 알아내고 맞는 파일 수천 개 전부의 미리보기를 만들고 있었다 — 내용 색인이 도는 중이면 "ai" 하나에 20초. 이제 (1) 조각 번호 → 파일을 메모리 표로 바꾼다(한 파일의 조각 번호는 이어져 있어 파일마다 [처음, 끝] 구간만, 켤 때 3~5초 미리 만듦 — `contentLookup`), (2) 미리보기는 화면에 보일 200개만 따로 만든다(`contentHits`, main의 `attachHits`). 같은 검색 30초 남짓 → 0.4~0.9초, 앱 화면에서 첫 결과 0.5초·끝까지 1.9초. 결과·미리보기가 예전 방식과 같은지 테스트로 견준다
- 두 글자 영문("ai")은 그 낱말만 찾는다 (전에는 ai로 시작하는 낱말 aim·air…까지)
- 이름 결과를 먼저 보여 준 뒤에는 "파일 목록을 불러오는 중…" 경고 대신 "아래는 이름으로 찾은 결과입니다. 파일 내용에서도 찾는 중…"
- 영문·숫자 한 글자("a")는 내용에서 찾지 않는다 — 거의 모든 문서에 있어 29초 걸렸다. 이름 정렬도 빨리(65만 개 결과 1.3초 → 0.5초)
- **띄어쓰기**: "설치정보"로 검색하면 본문의 "설치 정보"·"보고 서"(한 군데 띄어 쓴 것)와 이름 "설치 정보.xlsx"·"설치_정보.docx"도 찾는다 (`toMatchPhrase`가 나눈 형태를 OR로 더함, 이름은 띄어쓰기·밑줄을 뺀 이름 `compact`). 반대 방향("설치 정보" → "설치정보")은 전부터 됐다. 미리보기 강조도 같은 규칙
- **오탈자** (`fuzzy.js`): 정확히 맞는 결과가 30개 미만이면 한 글자만 다른 말로 한 번 더 찾아 뒤에 "비슷한 말"로 붙인다. 한글은 자모 하나(견젹서 → 견적서, 회의룩 → 회의록, 3음절 이상만 — 2음절은 "보고" → "보모"처럼 엉뚱한 게 너무 많다), 영문은 한 글자 바뀜·빠짐·더함·이웃 자리 바뀜(reprot → report, 4글자 이상). 내용은 색인에 실제 있는 낱말(`fts5vocab`)로만 고쳐 찾고, 고친 말 하나당 파일 200개까지

### 알려진 주의점

- 실행 중인 FindInside가 C:\ 전체를 감시하면 빌드 폴더를 읽어 빌드가 EPERM으로 실패한다 → `npm run dist`가 먼저 앱을 닫는다.
- 빌드 후에는 설치된 파일(`%LOCALAPPDATA%\Programs\findinside\resources\app`)에 변경이 들어갔는지 확인한다.
- 스토어에 새 패키지를 올리려면 `package.json` 버전을 올려야 한다 (예: 1.0.0 → 1.0.1).
- 새 버전 배포 순서: 버전 올리기 → `npm test` → `npm run dist` + `npm run dist:store` → GitHub 릴리스(findinside-download)에 Find_Setup.exe → Partner Center 새 제출에 appx → 판매 페이지는 푸시하면 Cloudflare(`site/`)와 Netlify(`netlify.toml` → `scripts/site-netlify.js`가 주소를 netlify.app으로 바꾼 복사본)에 각각 저절로 올라간다 (두 사이트는 서로 넘기지 않는다. 검색 엔진용 대표 주소는 netlify.app)
- 판매 페이지의 내려받기 단추는 `findinside.pages.dev/download/Find_Setup_v<버전>.exe`를 가리킨다 (옛 링크용 `Find_Setup.exe`도 릴리스마다 같이 올린다). 설치 파일이 108MB라 GitHub 릴리스 첨부에만 둘 수 있어서, Cloudflare Pages 함수(`functions/download/[file].js`)가 릴리스 `v<버전>`에서 받아 그대로 넘겨준다. 그래서 내려받은 파일의 출처가 github.com이 아니라 각 사이트 주소(pages.dev / netlify.app — Netlify는 `netlify.toml` 프록시로 pages.dev 함수를 거친다)로 찍히고 GitHub 앱도 열리지 않는다. 구매 링크는 새 탭에서 열린다.
- GitHub 릴리스는 이 PC의 `gh`(GitHub CLI, `kimheunghan` 로그인 완료)로 올린다. 100MB가 넘는 설치 파일은 저장소에 push할 수 없으므로 릴리스 첨부로만 올라간다.
