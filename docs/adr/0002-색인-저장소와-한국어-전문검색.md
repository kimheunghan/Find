# ADR-0002: 색인 저장소는 SQLite FTS5, 한국어는 2글자 단위(bigram)로 색인한다

**상태:** 제안 (Proposed)
**날짜:** 2026-09-28
**결정자:** kimheunghan
**관련:** ADR-0001 (엔진을 Electron/Node 안에 둔다)

## 배경

현재 색인은 모든 항목을 `findinside-index.json` 하나에 저장한다. 앱을 켤 때 전체를 메모리로 읽고, 검색할 때마다 모든 항목을 문자열 비교한다. 파일명만 다루는 지금은 동작하지만, 문서 내용을 색인하면 다음 문제가 생긴다.

- 문서 수만 개의 본문을 매번 통째로 읽고 쓸 수 없다 (증분 색인 불가, 기획문서 6.2)
- 검색마다 전체 본문을 훑으면 느리다
- 페이지·시트·셀 같은 내부 위치를 결과와 함께 돌려줘야 한다 (6.3)
- `AND`/`OR`/`NOT`, 따옴표 구문, 경로·형식·날짜 필터, 결과 내 재검색을 지원해야 한다 (5.2~5.4)

한국어 특성상 해결할 문제가 하나 더 있다. **조사·어미가 붙은 말**(`서버의`, `서버를`, `서버구축`)을 `서버`로 찾아야 한다. 또 업무 검색어는 `서버`, `사양`, `견적`처럼 **두 글자인 경우가 많다.**

- SQLite FTS5 기본 토크나이저(`unicode61`)는 공백·문장부호로만 단어를 나눈다. 그래서 `서버의`는 한 단어가 되고, `서버`로 검색하면 나오지 않는다.
- FTS5 내장 `trigram` 토크나이저는 부분 문자열 검색이 되지만, 세 글자 미만 검색어는 색인을 쓰지 못한다. 흔한 두 글자 한국어 검색어가 여기에 걸린다.

## 결정

1. 색인 저장소를 **SQLite 파일 하나**로 바꾸고, 전문 검색에는 **FTS5**를 쓴다. 파일 위치는 지금과 같은 사용자 데이터 폴더다.
2. Node 드라이버는 **`better-sqlite3`** 를 쓴다. 앞으로 Electron에 내장된 `node:sqlite`가 안정화되고 FTS5 포함이 확인되면 교체를 다시 검토한다.
3. 본문은 **앱이 직접 2글자 단위(bigram)로 잘라** 넣고, FTS5에는 공백으로 나눈 토큰만 넘긴다. 예를 들어 `서버구축` → `서버 버구 구축`이 된다. 검색어도 같은 방식으로 잘라 구문 검색으로 찾는다.
   - 영문·숫자 연속 구간은 단어 단위 토큰도 함께 넣는다. IP 주소 같은 정확 검색이 여기에 해당한다(기획문서 5.1).
   - 한 글자 검색어만 색인 없이 `LIKE`로 훑는다. 드문 경우로 보고 느려도 허용한다.
4. 문서는 **조각(chunk) 단위**로 저장한다. 조각마다 내부 위치(페이지, 시트·셀, 슬라이드, 문단, 발언 시간)를 붙이고, 검색 결과에서 FTS5 `snippet()`으로 일치 부분 미리보기를 보여 준다.
5. 증분 색인은 파일별 `수정 시각 + 크기`를 저장해 두었다가, 바뀐 파일만 다시 추출하는 방식으로 한다.

### 스키마 초안

```sql
CREATE TABLE files (
  id INTEGER PRIMARY KEY,
  path TEXT UNIQUE NOT NULL,
  name TEXT NOT NULL,
  kind TEXT NOT NULL,          -- file | folder
  extension TEXT,
  size INTEGER,
  modified_at INTEGER,
  content_status TEXT          -- pending | done | unsupported | error
);

CREATE TABLE chunks (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
  location TEXT,               -- JSON: {"page":3} / {"sheet":"서버","cell":"B4"} 등
  text TEXT NOT NULL           -- 원문(미리보기용)
);

-- 파일명·경로와 본문 토큰(bigram + 단어)을 따로 둔다
CREATE VIRTUAL TABLE name_fts USING fts5(tokens, content='');
CREATE VIRTUAL TABLE chunk_fts USING fts5(tokens, content='');
```

## 검토한 선택지

### 선택지 A: SQLite FTS5 + 앱에서 만든 bigram 토큰 (채택)

| 항목 | 평가 |
|------|------|
| 복잡도 | 중간. 토큰화 함수 하나를 직접 관리 |
| 한국어 검색 | 조사가 붙어도, 두 글자 검색어여도 색인으로 찾음 |
| 색인 크기 | 원문보다 커짐(대략 2~3배 예상, 측정 필요) |
| 기능 | `AND`/`OR`/`NOT`, 구문, `snippet()`, SQL 필터를 FTS5와 SQL로 바로 처리 |

**장점:** 형태소 분석기 없이도 한국어 부분 검색이 된다. 사전을 따로 관리할 필요가 없다. SQLite 안에서 필터와 전문 검색을 한 번에 처리한다.
**단점:** 짧은 검색어는 의도하지 않은 결과가 섞일 수 있다(예: `사과`로 검색하면 `감사과`도 나옴). 관련도 정렬로 보완해야 한다. 색인이 커진다.

### 선택지 B: SQLite FTS5 내장 `trigram` 토크나이저

| 항목 | 평가 |
|------|------|
| 복잡도 | 낮음. 설정 한 줄 |
| 한국어 검색 | 세 글자 이상은 좋음. 두 글자 검색어는 색인을 쓰지 못함 |
| 색인 크기 | bigram보다 큼 |

**장점:** 구현이 가장 간단하다.
**단점:** 가장 흔한 두 글자 검색어에서 약하다.

### 선택지 C: 한국어 형태소 분석기 + 단어 색인

| 항목 | 평가 |
|------|------|
| 복잡도 | 높음. 사전·분석기를 번들해야 하고, 신조어·고유명사·제품명에 약함 |
| 한국어 검색 | 정확도는 높지만 사전에 없는 말(서버 이름, 프로젝트 코드)을 놓침 |

**장점:** 결과가 깔끔하다.
**단점:** Node에서 쓸 만한 선택지가 적고 설치 크기가 커진다. 업무 자료의 고유명사에 약하다. 나중에 bigram 위에 가중치로 더하는 방식은 가능하다.

### 선택지 D: JSON 유지 + 메모리 검색 (현재)

본문 색인과 증분 색인이 불가능하다. 제외한다.

## 트레이드오프 분석

결정을 가르는 것은 **두 글자 한국어 검색어를 색인으로 찾을 수 있느냐** 와 **구현·배포 부담** 이다.

- trigram(B)은 가장 간단하지만, 실제로 가장 많이 입력할 검색어 형태에서 약하다.
- 형태소 분석(C)은 정확하지만 비싸고, 업무 자료의 고유명사를 놓친다. 기획문서의 "파일명을 몰라도 내용으로 찾는다"는 목표에 비해 재현율이 떨어진다.
- bigram(A)은 재현율이 높고 잡음이 조금 있다. 기획문서 8장이 "시스템은 후보를 좁히고 사람이 최종 판단한다"는 방향이므로, 놓치는 것보다 조금 넓게 찾는 편이 제품 원칙에 맞다.

## 결과

**쉬워지는 것**
- 증분 색인: 바뀐 파일의 행만 지우고 다시 넣으면 된다
- 필터와 결과 내 재검색: `files` 컬럼에 대한 SQL 조건으로 처리한다
- 검색 근거 표시: `snippet()`과 `location`으로 "3페이지에서 `WEB SERVER` 발견" 같은 설명을 만들 수 있다

**어려워지는 것**
- `better-sqlite3`는 네이티브 모듈이라 Electron 버전에 맞춰 다시 빌드해야 한다(`@electron/rebuild`)
- 관련도 정렬을 bigram 일치만으로 하면 부정확하다. 파일명 일치, 구문 연속 일치, 단어 경계 일치 가중치를 따로 설계해야 한다
- 토큰화 방식을 바꾸면 전체를 다시 색인해야 한다. DB에 토큰화 버전을 저장해 두고, 버전이 바뀌면 재색인하도록 한다

**다시 볼 시점**
- 샘플 자료로 측정한 색인 크기나 속도가 기준을 넘을 때
- 의미 검색(임베딩)을 붙일 때. 벡터 저장소를 같은 SQLite에 둘지는 별도 ADR로 정한다
