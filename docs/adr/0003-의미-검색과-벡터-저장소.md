# ADR-0003: 의미 검색은 로컬 다국어 임베딩 + 같은 SQLite(sqlite-vec)로 하고, 키워드 결과와 RRF로 합친다

**상태:** 제안 (Proposed)
**날짜:** 2026-09-28
**결정자:** kimheunghan
**관련:** ADR-0001 (엔진을 Electron/Node 안에 둔다), ADR-0002 (SQLite FTS5 + bigram)

## 배경

기획문서는 파일명과 단어가 일치하지 않아도 관련 자료를 찾아야 한다고 요구한다(1장, 5.1). 예를 들어 사용자가 `서버 IP와 시스템 사양 관련 자료`라고 검색하면, 파일명이 `설치정보.xlsx`이고 본문에 `WEB01 / 10.0.3.21 / CPU 8core`만 있는 파일이 결과에 나와야 한다. ADR-0002의 bigram 전문 검색은 **글자가 일치할 때만** 찾으므로 이런 개념 질의에는 약하다. 그래서 의미 검색을 따로 둔다.

ADR-0002는 "벡터 저장소를 같은 SQLite에 둘지는 별도 ADR로 정한다"고 미뤄 두었다. 이 ADR에서 그것을 정한다.

제약:

- **Local-First:** 문서 원문과 검색어를 외부 AI로 보내지 않는다(10장). 임베딩도 PC에서 계산한다.
- **단일 설치 파일:** Python 런타임을 넣지 않는다(11.1, ADR-0001).
- **설명 가능성:** "의미적으로 관련"이라는 근거와 함께 어느 조각이 관련되었는지 보여 줘야 한다(7장).
- **정확 검색 우선:** IP 주소, 고유번호, 따옴표 구문은 정확 검색 결과가 위에 와야 한다(5.1).
- **일반 사무용 PC:** GPU가 없다고 가정한다. 색인은 백그라운드에서 느리게 돌아도 되지만, 검색은 1초 안에 끝나야 한다.
- **규모 가정:** 문서 1만 개, 조각 20만~50만 개 수준(ADR-0002 실행 항목 6과 같은 샘플로 측정한다).

## 결정

1. **임베딩 모델:** 다국어 소형 모델을 ONNX(int8 양자화)로 **transformers.js**에서 실행한다. 1순위 후보는 `multilingual-e5-small`(384차원)이다. 최종 선택은 실행 항목 2의 한국어 평가로 정한다.
   - e5 계열은 문서에는 `passage: `, 검색어에는 `query: `를 앞에 붙여야 한다. 이것은 모델 어댑터 안에 감춘다.
2. **모델 배포:** 모델 파일을 **설치 파일에 포함**한다. 첫 실행 때 내려받지 않는다. 회사 방화벽 안에서도 설치 직후부터 동작해야 하고, 외부 통신을 만들지 않기 위해서다.
3. **벡터 저장소:** ADR-0002와 **같은 SQLite 파일**에 **`sqlite-vec`** 확장을 불러와 `vec0` 가상 테이블로 둔다. 벡터 하나는 ADR-0002의 `chunks` 행 하나와 1:1로 대응한다.
   - 처음에는 전수 비교(brute-force)로 가장 가까운 조각을 찾는다. 속도가 부족하면 int8 또는 비트 양자화 벡터로 1차 후보를 고르고 float 벡터로 다시 정렬한다.
4. **결합 방식:** 키워드(FTS5) 상위 K개와 의미 검색 상위 K개를 **RRF(Reciprocal Rank Fusion)** 로 합친 뒤 파일 단위로 묶는다.
   - 검색어가 따옴표 구문이거나 IP·숫자·코드 형태이면, 의미 검색 가중치를 낮추거나 의미 검색을 건너뛴다.
   - 결과마다 근거를 따로 붙인다. 예: `키워드: "WEB SERVER" 발견 (Sheet1!B4)`, `의미: '서버 사양'과 관련 (3페이지 조각)`.
   - 경로·형식·날짜 필터는 `files` 테이블 SQL 조건으로 먼저 거른다. 그 뒤 두 검색을 그 범위 안에서만 돌린다.
5. **색인 흐름:** 임베딩은 텍스트 추출 **다음 단계**로 분리한다. `files.embed_status`(`pending | done | error`)를 두고, 우선순위가 낮은 worker에서 조금씩 처리한다. 앱을 껐다 켜도 이어서 한다. 임베딩이 끝나지 않은 파일도 키워드 검색으로는 바로 찾을 수 있다.
6. **모델 버전 관리:** DB에 `embedding_model`(이름·버전·차원)을 저장한다. 모델이 바뀌면 벡터만 다시 만든다. 추출된 텍스트는 다시 만들지 않는다.

### 스키마 추가분 (ADR-0002 초안에 더함)

```sql
ALTER TABLE files ADD COLUMN embed_status TEXT;   -- pending | done | error

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
-- ('embedding_model', '{"name":"multilingual-e5-small","rev":"...","dim":384}')

CREATE VIRTUAL TABLE chunk_vec USING vec0(
  chunk_id INTEGER PRIMARY KEY,   -- chunks.id
  embedding float[384]
);
```

## 검토한 선택지

선택할 축이 두 가지라서 따로 비교한다.

### 축 1. 벡터 저장소

#### 선택지 A: 같은 SQLite + sqlite-vec (채택)

| 항목 | 평가 |
|------|------|
| 복잡도 | 낮음. DB 파일 하나, 트랜잭션 하나 |
| 비용 | 없음(오픈소스, MIT/Apache-2.0) |
| 확장성 | 전수 비교라 조각 수에 비례해 느려짐. 50만 개 × 384차원 float이면 저장 공간 약 750MB, 검색 속도는 측정 필요 |
| 팀 익숙도 | ADR-0002와 같은 SQL로 다룸 |

**장점:** 파일을 지우거나 수정하면 조각·FTS·벡터를 한 트랜잭션에서 함께 지운다. 동기화가 깨질 일이 없다. 범위 필터와 조인을 SQL로 처리한다. 백업과 재색인이 파일 하나로 끝난다.
**단점:** `sqlite-vec`는 아직 1.0 전이라 API가 바뀔 수 있다. 근사 최근접(ANN) 색인이 없어 규모가 커지면 느려진다. `better-sqlite3`에 확장을 불러오는 네이티브 빌드와 배포를 확인해야 한다.

#### 선택지 B: SQLite + 별도 ANN 색인 파일 (hnswlib-node 등)

| 항목 | 평가 |
|------|------|
| 복잡도 | 중간. 색인 파일 두 개를 따로 동기화 |
| 확장성 | 좋음. 수백만 개에서도 빠름 |

**장점:** 큰 규모에서 검색이 빠르다.
**단점:** SQLite와 트랜잭션을 함께 쓸 수 없어서, 앱이 비정상 종료되면 두 색인이 어긋난다. 삭제된 항목을 처리하고 색인을 다시 만드는 로직이 따로 필요하다. 범위 필터를 먼저 적용하기 어렵다.

#### 선택지 C: 별도 벡터 DB 내장 (LanceDB 등)

**장점:** 벡터와 필터 검색 기능이 풍부하다.
**단점:** 저장소가 두 개가 되고, 네이티브 의존성이 늘어나고, 설치 크기도 커진다. 로컬 단일 사용자 규모에는 과하다.

#### 선택지 D: 메모리 배열(Float32Array)로 전수 비교

**장점:** 의존성이 없고 가장 단순하다.
**단점:** 앱을 켤 때마다 전체 벡터를 메모리로 읽어야 하고, 메모리를 수백 MB 쓴다. ADR-0002가 JSON 방식을 버린 이유와 같은 문제가 생긴다.

### 축 2. 임베딩 모델

| 후보 | 크기(int8, 대략) | 차원 | 평가 |
|------|------------------|------|------|
| `multilingual-e5-small` (1순위) | 약 100MB대 | 384 | CPU에서 빠르고 한국어를 지원한다. 품질은 중간 |
| `multilingual-e5-base` | 약 250MB대 | 768 | 품질이 한 단계 높다. 색인이 약 2~3배 느리고 저장 공간은 2배 |
| `bge-m3` | 약 500MB 이상 | 1024 | 다국어 품질은 높지만 사무용 CPU에서 색인이 오래 걸리고 설치 크기가 크다 |
| 외부 임베딩 API | 0 | - | Local-First 원칙에 어긋난다(10장). **제외** |

크기와 속도는 대략적인 값이다. 실행 항목 2에서 실제로 측정해 이 표를 고친다.

## 트레이드오프 분석

**저장소:** 결정을 가르는 것은 **데이터 정합성과 단순함(A 우세)** 과 **큰 규모에서의 검색 속도(B·C 우세)** 다.

- 이 제품은 PC 한 대, 사용자 한 명이 쓰고, 파일 추가·수정·삭제가 계속 일어난다. 이런 환경에서는 색인 두 개가 어긋나는 문제가 속도 문제보다 먼저, 더 자주 생긴다.
- 사용자는 대부분 경로·형식·기간 필터를 걸고 검색하므로(5.3, 5.4) 실제로 비교할 벡터 수는 전체보다 훨씬 적다.
- 그래서 A로 시작하고, 필터 없이 전체를 검색할 때 기준 시간을 넘으면 양자화 → B 순서로 옮긴다. 벡터가 `chunks.id` 기준으로 저장되어 있으므로 옮기는 비용이 크지 않다.

**모델:** 결정을 가르는 것은 **한국어 개념 질의 품질** 과 **사무용 CPU에서의 색인 시간·설치 크기** 다.

- 의미 검색은 키워드 검색을 **보완**한다. 정답을 확정하는 것은 사람의 검수다(8장). 그래서 최고 품질보다 "모든 파일에 끝까지 임베딩이 된다"는 점이 더 중요하다.
- 따라서 작은 모델로 시작하고, 한국어 평가에서 차이가 크게 날 때만 base급으로 올린다.

**결합:** RRF는 점수 척도가 서로 다른 두 검색(BM25 점수와 코사인 유사도)을 순위만으로 합친다. 가중치를 조정할 필요가 거의 없고, 근거도 "키워드 몇 위, 의미 몇 위"로 나누어 설명할 수 있다.

## 결과

**쉬워지는 것**
- 단어가 일치하지 않는 개념 질의로도 관련 자료가 후보에 오른다
- 파일 삭제·수정 시 텍스트·FTS·벡터를 한 트랜잭션에서 정리한다
- 경로·형식·날짜 필터를 키워드 검색과 의미 검색에 똑같이 적용한다
- 모델을 바꿀 때 벡터만 다시 만든다

**어려워지는 것**
- 설치 파일이 모델 크기만큼 커진다(약 100MB대 추가)
- `onnxruntime-node`와 `sqlite-vec`까지 네이티브 모듈이 늘어나 Electron 버전에 맞춘 빌드와 CI가 복잡해진다
- 첫 색인 뒤 임베딩이 끝날 때까지 의미 검색 결과가 불완전하다. 화면에 진행률을 보여 줘야 한다
- bigram 결과에 의미 결과가 섞이면서 잡음이 늘 수 있다. 근거 표시와 검수 UI가 이를 보완해야 한다

**다시 볼 시점**
- 필터 없는 전체 검색에서 의미 검색이 기준 시간(예: 500ms)을 넘을 때 → 양자화, 그다음 선택지 B
- 한국어 평가에서 recall@10이 기준에 못 미칠 때 → 모델을 base급으로 올리거나 한국어 특화 모델 검토
- `sqlite-vec`가 1.0을 내거나 API를 크게 바꿀 때
- 검수 결과(관련 있음/없음)를 순위에 반영하게 될 때 → 별도 ADR

## 실행 항목

1. [ ] Electron 38에서 `better-sqlite3` + `sqlite-vec` 확장 불러오기, `onnxruntime-node`(transformers.js) 실행을 확인한다. `@electron/rebuild`와 electron-builder로 빌드해 본다
2. [ ] **한국어 평가 세트:** 실제 업무 자료에서 질의와 정답 파일 30~50쌍을 만든다(개념 질의와 정확 질의를 섞는다). 키워드만 썼을 때와 결합했을 때의 recall@10을 비교하고, 후보 모델 2~3개의 색인 속도와 품질을 측정해 기준을 기록한다
3. [ ] 임베딩 어댑터 `embed(texts, kind: 'query' | 'passage') → Float32Array[]`를 worker에서 구현한다. 모델별 접두어와 최대 길이 처리를 여기에 감춘다
4. [ ] 조각 길이를 모델 최대 입력(e5 기준 512토큰)에 맞춘다. ADR-0002 추출기가 만드는 조각이 너무 길면 나눈다
5. [ ] `embed_status` 기반 백그라운드 임베딩 큐를 만든다. 일시정지와 재개, CPU 사용 제한, 진행률 표시를 넣는다
6. [ ] RRF 결합과 정확 질의 판별(따옴표, IP, 숫자·코드 패턴)을 구현하고 결과별 근거 문구를 만든다
7. [ ] 조각 1만/10만/50만 개에서 벡터 검색 시간, DB 크기, 메모리 사용량을 측정한다
8. [ ] 모델과 `sqlite-vec`, `onnxruntime`의 라이선스와 설치 파일 크기를 확인한다(ADR-0001 실행 항목 5와 함께)
