# ADR-0004: 메일은 앱이 직접 가져와 텍스트만 색인하고, 원본은 서버 참조로 두며, 인증정보는 Windows DPAPI로 암호화한다

**상태:** 제안 (Proposed)
**날짜:** 2026-09-28
**결정자:** kimheunghan
**관련:** ADR-0001 (Node 엔진), ADR-0002 (SQLite FTS5 + bigram), ADR-0003 (의미 검색)

## 배경

기획문서 v1은 메일 세 가지를 검색 대상으로 정한다(4.2).

- **Microsoft 365 / Outlook:** Microsoft Graph API + OAuth
- **범용 IMAP:** 서버·포트·보안 방식(SSL/TLS, STARTTLS, 없음)·계정·인증정보를 사용자가 입력한다. 포트 같은 값을 하드코딩하지 않는다
- **MSG / EML:** 로컬에 저장된 메일 파일. 내부 첨부파일까지 분석한다

검색 대상은 제목, 본문, 발신자·수신자·참조, 날짜, 첨부파일명, 첨부파일 내부 내용이다. 메일 필터(5.3)와 수집함(9장)도 메일을 다뤄야 한다.

지금 엔진은 로컬 파일만 알고, ADR-0002 스키마의 `chunks`도 `files`에만 연결된다. 메일을 넣으려면 다음을 정해야 한다.

1. 메일과 첨부파일을 색인 DB에 어떤 모양으로 넣을지
2. 메일 원문과 첨부파일 원본을 PC에 저장할지
3. 서버와 증분 동기화하는 방식
4. OAuth 토큰과 IMAP 비밀번호를 보관하는 방식(10장: 평문 저장 금지, 로그에 남기지 않기)

## 결정

1. **공통 메일 모델:** 연동 방식마다 커넥터를 두고, 모두 같은 정규화된 메일 객체를 내보낸다.
   - 메일 객체: `{ account, folder, remoteId, subject, from, to, cc, date, bodyText, attachments[] }`
   - 커넥터 인터페이스: `listFolders()`, `sync(folder, cursor) → { messages, deletedIds, nextCursor }`, `fetchAttachment(remoteRef)`
   - 커넥터는 Graph, IMAP, 로컬 파일(MSG/EML) 세 가지다. 로컬 파일은 파일 색인 경로에서 호출한다.
2. **첨부파일도 파일과 같은 추출기로 처리한다.** ADR-0001의 `extract(path) → [{ text, location }]`를 `extract(buffer, name)`로도 부를 수 있게 넓힌다. 첨부된 MSG/EML은 재귀로 풀되 **깊이 3단계**까지만 푼다. 압축파일(ZIP)은 v1 범위 밖이라 파일명만 색인한다.
3. **PC에는 추출한 텍스트와 메타데이터만 저장한다.** 메일 원문(MIME)과 첨부파일 원본은 저장하지 않는다. 대신 서버 위치(Graph 메시지·첨부 ID, IMAP `UIDVALIDITY`·`UID`·파트 번호)를 저장한다.
   - 미리보기에는 저장된 텍스트 조각을 쓴다.
   - 사용자가 첨부파일을 열거나 **실제 수집**(복사)을 할 때만 서버에서 다시 받는다.
4. **Microsoft 365:** `@azure/msal-node`로 **공개 클라이언트 + PKCE + 시스템 브라우저 + loopback 리디렉션**을 쓴다.
   - 권한은 `Mail.Read`, `offline_access`, `User.Read`만 요청한다(위임 권한, 읽기 전용).
   - 증분 동기화는 폴더별 **Graph delta 쿼리**로 한다. `deltaLink`를 커서로 저장한다.
   - 429 응답이 오면 `Retry-After` 값을 따른다.
5. **범용 IMAP:** 접속은 `imapflow`, 메일 파싱은 `mailparser`로 한다.
   - 사용자가 입력한 서버·포트·보안 방식을 그대로 쓴다. 앱에는 보안 방식별 **추천값만** 미리 채운다.
   - 보안 방식을 `없음`으로 고르면 비밀번호가 평문으로 전송된다고 경고하고 확인을 받는다.
   - 증분 동기화: 폴더별 `UIDVALIDITY`와 마지막 `UID`를 저장하고, 새 UID만 가져온다. `UIDVALIDITY`가 바뀌면 그 폴더만 다시 색인한다.
   - 삭제된 메일: 서버가 `QRESYNC`를 지원하면 그것으로 반영한다. 지원하지 않으면 주기적으로 UID 목록을 비교해 반영한다.
   - v1 인증은 계정 비밀번호 또는 앱 비밀번호다. IMAP용 OAuth(XOAUTH2)는 요구가 생기면 추가한다.
6. **MSG/EML:** 파일 색인 과정에서 `.eml`은 `mailparser`, `.msg`는 `@kenjiuno/msgreader`로 파싱한다. 결과는 결정 1의 메일 객체로 바꿔 같은 테이블에 넣는다. 이런 메일은 원본이 로컬 파일이므로 `source='file'`로 저장하고 파일 경로를 참조로 쓴다.
7. **인증정보 보관:** Electron **`safeStorage`**(Windows에서는 DPAPI)로 암호화해 SQLite `accounts.secret` 열에 저장한다.
   - MSAL 토큰 캐시는 캐시 플러그인으로 같은 방식으로 암호화한다.
   - 로그에는 계정 주소까지만 남긴다. 토큰, 비밀번호, 메일 본문은 로그에 남기지 않는다.
   - `safeStorage.isEncryptionAvailable()`가 `false`이면 저장하지 않는다. 매번 입력하게 하고 이유를 안내한다.
8. **동기화 실행:** 네트워크 동기화와 텍스트 추출은 **서로 다른 큐**로 돌린다. 서버가 느리거나 막혀도 로컬 파일 색인은 멈추지 않는다. 계정마다 동시 요청 수를 제한한다.

### 스키마 추가분 (ADR-0002 초안에 더함)

```sql
CREATE TABLE accounts (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,            -- graph | imap
  address TEXT NOT NULL,
  config TEXT NOT NULL,          -- JSON: IMAP 서버·포트·보안 방식 등 (비밀 아님)
  secret BLOB                    -- safeStorage로 암호화한 토큰 캐시·비밀번호
);

CREATE TABLE mail_folders (
  id INTEGER PRIMARY KEY,
  account_id INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  remote_id TEXT NOT NULL,
  name TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  cursor TEXT                    -- Graph deltaLink 또는 {"uidValidity":..,"lastUid":..}
);

CREATE TABLE messages (
  id INTEGER PRIMARY KEY,
  source TEXT NOT NULL,          -- graph | imap | file
  folder_id INTEGER REFERENCES mail_folders(id) ON DELETE CASCADE,
  file_id INTEGER REFERENCES files(id) ON DELETE CASCADE,   -- MSG/EML이면 원본 파일
  parent_attachment_id INTEGER REFERENCES attachments(id) ON DELETE CASCADE, -- 첨부된 메일
  remote_ref TEXT,               -- JSON: 서버 위치
  subject TEXT, sender TEXT, recipients TEXT, cc TEXT,
  sent_at INTEGER
);

CREATE TABLE attachments (
  id INTEGER PRIMARY KEY,
  message_id INTEGER NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  extension TEXT,
  size INTEGER,
  remote_ref TEXT,               -- 서버에서 다시 받을 때 쓰는 위치
  content_status TEXT            -- pending | done | unsupported | error
);

-- chunks는 파일·메일 본문·첨부파일 중 정확히 하나에 속한다
ALTER TABLE chunks ADD COLUMN message_id INTEGER REFERENCES messages(id) ON DELETE CASCADE;
ALTER TABLE chunks ADD COLUMN attachment_id INTEGER REFERENCES attachments(id) ON DELETE CASCADE;
-- (file_id는 NULL 허용으로 바꾸고, 셋 중 하나만 채워졌는지 확인하는 CHECK를 둔다.
--  SQLite는 ALTER로 제약을 바꿀 수 없으므로, ADR-0002 구현 시 처음부터 이 형태로 만든다)
```

## 검토한 선택지

### 선택지 A: 앱이 직접 연동하고, 텍스트만 저장 + 원본은 서버 참조 (채택)

| 항목 | 평가 |
|------|------|
| 복잡도 | 중간. 커넥터 3개, 공통 모델 하나 |
| 디스크 사용 | 작음. 텍스트와 메타데이터만 저장 |
| 보안 | 민감한 원본의 복사본이 PC에 새로 생기지 않음 |
| 오프라인 | 검색·미리보기는 됨. 첨부파일 열기·실제 수집은 서버 연결 필요 |

**장점:** 메일함 크기(수 GB)만큼 디스크를 더 쓰지 않는다. 서버에서 메일이 지워지면 색인에서도 지워지므로, 회사 보존 정책과 크게 어긋나지 않는다.
**단점:** 추출기나 토큰화 방식이 바뀌면 첨부파일을 서버에서 다시 받아야 한다. 오프라인에서는 첨부 원본을 열 수 없다.

### 선택지 B: 메일 원문(.eml)과 첨부파일을 PC에 통째로 캐시

| 항목 | 평가 |
|------|------|
| 복잡도 | 낮음~중간. 동기화한 뒤에는 로컬 파일처럼 다룸 |
| 디스크 사용 | 큼. 메일함 전체 크기만큼 |
| 보안 | 민감한 원본의 사본이 앱 데이터 폴더에 쌓임. 암호화와 삭제 정책이 따로 필요 |

**장점:** 오프라인에서도 모두 열 수 있다. 재색인할 때 네트워크가 필요 없다.
**단점:** 디스크 부담이 크고, 로컬에 관리 대상 데이터가 새로 생긴다. Local-First는 "외부로 보내지 않는다"는 원칙이지 "모든 것을 복사해 둔다"는 뜻이 아니다.

### 선택지 C: PC에 설치된 Outlook을 통해 읽기 (COM/MAPI, PST/OST)

**장점:** 서버 인증을 따로 구현하지 않아도 된다.
**단점:** 클래식 Outlook이 설치되어 있어야 하고, 새 Outlook에는 COM/PST가 없다. PST/OST는 기획문서상 후속 기능(13장)이다. **제외.**

### 선택지 D: Microsoft 365도 IMAP으로 통일

**장점:** 커넥터가 하나로 줄어든다.
**단점:** Microsoft 365의 IMAP도 결국 OAuth가 필요하다. 많은 회사가 IMAP을 꺼 두기도 한다. 폴더별 delta 동기화도 쓸 수 없다. 기획문서가 Graph를 명시한다(4.2). **제외.**

### 인증정보 보관 방식 비교

| 방식 | 평가 |
|------|------|
| Electron `safeStorage` (채택) | Electron에 내장되어 있고, Windows에서는 사용자 계정에 묶인 DPAPI를 쓴다. 네이티브 모듈을 추가하지 않는다 |
| `keytar` (Windows 자격 증명 관리자) | 저장소가 보관(archive) 상태라 유지보수가 불확실하다. 네이티브 모듈이 하나 더 늘어난다 |
| 앱 자체 키로 AES 암호화 | 키를 어딘가에 둬야 하므로 사실상 평문과 같다. **제외** |

## 트레이드오프 분석

결정을 가르는 것은 **오프라인 가용성·재색인 편의(B 우세)** 와 **디스크 사용량·민감 데이터 복제 최소화(A 우세)** 다.

- 사용자는 대부분 검색하고, 미리보기로 확인하고, 검수한다. 원본이 필요한 순간은 후보를 연 뒤 첨부를 열거나 수집할 때뿐이다. 그 순간에만 서버에 접속하는 비용은 작다.
- 메일함 전체를 로컬에 복제하면 회사 보안 정책과 부딪힐 수 있다. 제품 원칙(10장)과 조직 사용자 대상(3.1)을 생각하면 A가 더 설명하기 쉽다.
- 재색인 비용은 버전을 관리해 줄인다. 추출기 버전이 바뀌어도 이미 추출한 텍스트를 다시 토큰화하는 데는 원본이 필요 없다. 원본을 다시 받는 것은 **추출기 자체가 바뀐 형식**의 첨부파일뿐이다.

## 결과

**쉬워지는 것**
- 파일·메일·첨부파일이 같은 `chunks` → FTS5 → 벡터 흐름을 탄다. 검색·근거·필터 코드를 따로 만들지 않아도 된다
- 메일 필터(발신자·기간·첨부 유무)를 `messages` SQL 조건으로 처리한다
- 새 메일 서비스는 커넥터 하나만 추가하면 된다(후속: Gmail, PST)

**어려워지는 것**
- Graph 사용을 위해 Azure 앱 등록(멀티테넌트 공개 클라이언트)이 필요하다. 일부 회사는 사용자 동의를 막아 두어 **관리자 동의**를 받아야 한다
- IMAP 서버마다 확장 기능 지원이 달라서, 삭제 반영과 증분 동기화를 서버별로 확인해야 한다
- `safeStorage`로 암호화한 값은 Windows 사용자 계정에 묶인다. PC를 옮기거나 Windows 계정을 바꾸면 다시 로그인해야 한다
- 결정 3 때문에 오프라인에서는 첨부파일 열기와 실제 수집이 실패한다. 화면에서 이유를 분명히 안내해야 한다

**다시 볼 시점**
- 오프라인 수집 요구가 실제로 나올 때 → 선택한 메일만 원본을 캐시하는 방식 검토
- 대상 회사 IMAP 서버에서 비밀번호 인증이 막혀 있을 때 → XOAUTH2 추가
- 메일 수가 계정당 10만 통을 넘어 초기 동기화 시간이 기준을 넘을 때

## 기획문서에 확인이 필요한 사항

기획문서 14장에 따라, 아래 해석은 구현 전에 PRD에 반영하고 합의한다.

1. **메일 색인 범위:** 폴더 선택과 기간(예: 최근 N년) 제한을 둘지. 파일의 "색인 범위 / 검색 범위" 구분(5.3)을 메일에도 적용할지
2. **첨부파일 원본 비저장(결정 3):** 오프라인에서 첨부파일을 열 수 없다는 제약을 받아들일지
3. **첨부파일 크기 상한:** 예를 들어 50MB를 넘는 첨부는 파일명만 색인할지

## 실행 항목

1. [ ] ADR-0002 스키마를 구현할 때 `chunks`가 파일·메일·첨부파일 중 하나에 속하도록 처음부터 설계한다
2. [ ] 추출기 인터페이스에 `extract(buffer, name)` 경로를 추가하고, EML/MSG 파서와 재귀 첨부 처리(깊이 3단계)를 만든다. 테스트용 샘플에는 한글 파일명, 인코딩이 섞인 메일, 첨부 속 첨부를 넣는다
3. [ ] 커넥터 인터페이스와 가짜(mock) 커넥터로 동기화 큐, 커서 저장, 삭제 반영을 먼저 테스트한다
4. [ ] IMAP 커넥터: 실제 회사 IMAP 서버 1곳 이상과 Dovecot 테스트 서버에서 SSL/TLS·STARTTLS 접속, 증분 동기화, `UIDVALIDITY` 변경 처리를 확인한다
5. [ ] Azure 앱 등록, MSAL loopback 로그인, 폴더별 delta 동기화를 만들고 개발 테넌트에서 관리자 동의가 필요한 경우의 안내 화면을 확인한다
6. [ ] `safeStorage` 기반 비밀 저장소와 MSAL 캐시 플러그인을 만든다. 로그에 비밀이 남지 않는지 확인하는 테스트를 넣는다
7. [ ] 위 "확인이 필요한 사항" 세 가지를 기획문서에 반영하고 합의한다
8. [ ] `imapflow`, `mailparser`, `@kenjiuno/msgreader`, `@azure/msal-node`의 라이선스를 확인한다(ADR-0001 실행 항목 5와 함께)
