# ADR-0001: 내용 추출·검색 엔진을 Electron(Node) 안에 둔다

**상태:** 제안 (Proposed)
**날짜:** 2026-09-28
**결정자:** kimheunghan

## 배경

현재 `main`의 PC 앱은 Electron + Node로 되어 있고 파일명·폴더명·경로만 색인한다(`src/`). 다음 단계는 문서 내부 텍스트 추출이며, 이후 기획문서 v1 범위(HWP/HWPX, DOC~PPTX, PDF, MSG/EML, IMAP·Microsoft 365, M4A STT, 의미 검색)로 넓혀야 한다.

한편 별도 작업(`feat/pc-app-mvp-rebased` 패치)은 `src/`를 지우고 Python 엔진(`engine/`)과 새 UI(`app/`)로 교체하는 방향을 제안했다. 두 방향을 동시에 유지할 수 없으므로 지금 엔진의 런타임을 정해야 한다.

제약(기획문서 기준):

- 사용자가 Python·Node를 따로 설치하지 않는 단일 설치 파일 `Find_Setup.exe` (11.1)
- 문서·검색 DB·가능한 의미 검색까지 로컬 처리 (10)
- HWP/HWPX 지원은 필수 (4.1)
- 결과에 페이지·시트·셀·슬라이드·발언 시간 등 내부 위치 표시 (6.3)
- 첫 실행 후 증분 색인 (6.2)

현재 색인은 전체 항목을 JSON 파일 하나에 저장하고 메모리에서 선형 검색한다. 파일 내용까지 담으면 이 방식은 유지할 수 없다.

## 결정

1. **엔진은 Electron 메인 프로세스 쪽 Node 코드로 계속 만든다.** 기존 `src/` 구현 위에서 확장한다.
2. **색인 저장소를 JSON에서 SQLite(FTS5 전문 검색)로 바꾼다.** 내용 추출보다 먼저 한다.
3. **파싱은 worker thread에서 돌려** UI와 메인 프로세스가 멈추지 않게 한다.
4. Node 라이브러리로 안 되는 작업(예: 이미지 OCR)은 **Windows 기본 기능이나 함께 배포하는 네이티브 실행 파일**을 자식 프로세스로 호출한다. Python 런타임은 넣지 않는다.
5. 단, **HWP 파싱 검증에서 Node 쪽이 기준에 못 미치면** 해당 형식만 Python 추출기를 PyInstaller 단일 실행 파일로 번들하는 방안을 다시 검토한다(ADR 개정).

## 검토한 선택지

### 선택지 A: Electron + Node 단일 런타임 (+ 필요한 네이티브 바이너리)

| 항목 | 평가 |
|------|------|
| 복잡도 | 낮음~중간. 프로세스 하나, 언어 하나 |
| 배포 | electron-builder 하나로 `Find_Setup.exe` 생성 |
| 형식 지원 | HWPX·DOCX·XLSX·PPTX(zip+XML), PDF(pdf.js), XLS(SheetJS), MSG/EML, IMAP, Graph 모두 Node 라이브러리 있음. HWP 5.0·DOC·PPT(구형 바이너리)는 선택지가 적음 |
| 의미 검색 | transformers.js(ONNX)로 다국어 임베딩 모델을 로컬 실행 가능 |
| 기존 코드 | 그대로 이어서 사용 |

**장점:** 기존 구현과 테스트를 버리지 않는다. 설치 파일이 단순하다. 앱 내부 통신(IPC)이 하나뿐이다.
**단점:** HWP·DOC·PPT 구형 바이너리 파서의 품질과 유지보수 상태가 Python보다 불확실하다. 무거운 작업이 메인 프로세스를 막지 않도록 worker 구성이 필요하다.

### 선택지 B: Python 엔진 사이드카 + Electron UI

| 항목 | 평가 |
|------|------|
| 복잡도 | 높음. 두 런타임, 프로세스 간 통신(HTTP/stdio), 엔진 수명 관리 |
| 배포 | PyInstaller로 엔진을 묶은 뒤 Electron 설치 파일에 포함. 설치 크기 증가, 백신 오탐 사례 잦음 |
| 형식 지원 | 문서 파서·OCR·임베딩 생태계가 가장 넓음 |
| 의미 검색 | sentence-transformers 등 선택지가 많음 |
| 기존 코드 | `src/` 폐기 후 재작성 |

**장점:** 파서와 ML 라이브러리 선택지가 넓다.
**단점:** 기존 구현을 버린다. 설치 파일 빌드가 Windows에서 실제로 되는지 아직 확인하지 못했다. 쓸 만한 Python 파서 일부는 AGPL/GPL 라이선스라 배포 제품에 넣기 전에 검토가 필요하다.

### 선택지 C: 네이티브 엔진(Rust/C#) + UI

파싱·색인 성능과 배포 크기는 가장 좋지만, 현재 팀 규모와 MVP 단계에서 새 언어와 파서 생태계를 들이는 비용이 크다. 이번에는 제외한다.

## 트레이드오프 분석

결정을 가르는 것은 **파서 생태계의 넓이(B 우세)** 와 **배포·유지 단순성 및 기존 코드 보존(A 우세)** 이다.

- 기획문서 v1 형식 중 대부분(HWPX, OOXML 3종, PDF, TXT/CSV, EML, MSG, XLS)은 Node에서도 충분히 처리할 수 있다. 불확실한 것은 HWP 5.0, DOC, PPT 세 가지다.
- 따라서 불확실성이 일부 형식에 한정된 상태에서 런타임 전체를 바꾸는 것(B)은 과하다. A로 가되 HWP를 가장 먼저 검증해 되돌릴 지점을 명확히 둔다.

## 결과

**쉬워지는 것**
- 설치 파일 하나, 런타임 하나로 빌드·배포·디버깅
- 기존 UI·색인·테스트를 그대로 확장
- SQLite FTS5로 증분 색인(파일별 수정 시각 비교)과 결과 내 재검색 필터를 SQL로 처리

**어려워지는 것**
- 구형 바이너리 형식(HWP 5.0, DOC, PPT) 파서를 직접 보완해야 할 수 있음
- `better-sqlite3`, `onnxruntime-node` 같은 네이티브 모듈을 Electron 버전에 맞춰 다시 빌드해야 함

**다시 볼 시점**
- HWP 검증 결과가 기준에 못 미칠 때(결정 5)
- 의미 검색 모델의 한국어 품질이나 속도가 부족할 때
