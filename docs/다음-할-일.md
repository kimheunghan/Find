## 1. Cloudflare Pages로 판매 페이지 옮기기 — **주소 고치기는 끝남, 사이트 만들기만 남음**

Netlify는 크레딧이 떨어져 배포가 멈췄다. 사용자는 Cloudflare 계정(`jocbo.pages.dev` 운영 중)에 여유가 있어 그쪽으로 옮기기로 했다. **새 주소는 `https://findinside.pages.dev`로 정했다**(2026-10-07, 도메인은 사지 않기로 함).

**끝난 것**: 저장소 안 `findinside.netlify.app` 32군데를 `findinside.pages.dev`로 바꿔 커밋했다 (`site/sitemap.xml` 7, 형식별 안내 4개 각 5, `site/robots.txt`, `src/product.json`, README·문서 3). 형식별 안내와 `robots.txt`·`sitemap.xml`은 `npm run docs`가 만드는 파일이 **아니라** `site/`에 직접 든 파일이라 손으로 고쳤다 — 앞으로도 그렇다.

**남은 것 ① Cloudflare Pages 프로젝트 만들기 (사용자가 브라우저에서)**

dash.cloudflare.com → Workers & Pages → Create → Pages → Connect to Git → `kimheunghan/Find` 선택:

| 항목 | 값 |
|---|---|
| 프로젝트 이름 | `findinside` (주소가 `findinside.pages.dev`가 된다) |
| 프로덕션 브랜치 | `main` |
| 빌드 명령 | **비워 둠** |
| 빌드 출력 디렉터리 | `site` |

저장소를 연결해 두면 푸시할 때마다 자동 배포된다. `site/`가 저장소에 그대로 들어 있어 빌드가 필요 없다. 비공개 저장소여도 된다.

**검색 노출 상태 (2026-10-09)**
- 네이버: 오늘 두 주소 모두 서치어드바이저에 등록(소유확인·robots.txt 수집). 아직 검색에 안 나온다 (사용자 확인) — 수집까지 며칠~몇 주.
- 구글 netlify.app: 사이트맵 10-03 제출·10-07 읽음 "성공", 페이지 7개 발견. 10-09 첫 페이지 URL 검사 "URL을 Google에 등록할 수 있음", 색인 생성 요청함.
- 구글 pages.dev: 10-09 속성 등록·사이트맵 제출 → "사이트맵을 읽을 수 없음", 발견 0. 파일은 정상이다 (Googlebot으로 받으면 200·`application/xml`, netlify 것과 주소만 다르고 같음, 안의 주소 7개 모두 넘김 없이 200). 새로 만든 속성에서 흔히 뜨는 일시 상태라 며칠 뒤 다시 본다. 그래도 그대로면 사이트맵을 지우고 다시 제출. 10-10 구글 `site:findinside.pages.dev` 결과 0건 (등록 하루째라 예상대로). URL 검사로 첫 페이지·안내 4개 색인 요청이 필요하다. 1~2주 지나도 0건이면, 내용이 같은 netlify.app을 구글이 대표로 고른 것일 수 있다.
- 구글 결과 페이지는 자동으로 읽을 수 없어(자바스크립트 필요) 노출 여부는 사람이 `site:` 검색이나 서치 콘솔 "실적"으로 확인한다.
- 다른 검색 엔진으로 "FindInside 문서 속 글자까지 찾는 PC 검색"을 찾으면 우리 것은 `github.com/kimheunghan/findinside-download`만 나오고, **같은 이름의 다른 프로그램**(tkosoft.com의 무료 FindInside 2.x, Softpedia 등 소개 글)이 위를 차지한다. 이름만으로 검색하면 그쪽과 섞인다.
- 두 사이트 내용이 같아 검색 엔진이 한쪽만 대표로 고를 수 있다 — 따로 두기로 한 결정(1-1)에 따른 감수 사항.

**남은 것 ② 구글 서치 콘솔**: 주소가 바뀌면 다른 사이트로 보므로 `findinside.pages.dev` 속성을 새로 추가·확인하고 사이트맵(`https://findinside.pages.dev/sitemap.xml`)을 제출한다. 확인용 `<meta name="google-site-verification">`은 `site/index.html`에 이미 있고 보통 계정 단위라 그대로 통과한다. 새 속성 화면에 다른 태그가 나오면 그걸로 바꾼다. **기존 netlify 속성은 지우지 않는다.**

**남은 것 ③ 저장소 밖 주소** (사용자가 직접): Partner Center 목록의 웹사이트·지원 주소, Lemon Squeezy 가게 설정. `findinside-download` 저장소 README는 `gh`로 대신 고칠 수 있다.

`src/product.json`의 주소는 앱 **정보** 창에 뜨므로 다음 빌드(1.0.4)부터 반영된다.

## 1-1. Netlify 사이트는 따로 둔다 — 리디렉션 안 함, 자기 주소로 저절로 올라감

**결정(2026-10-08)**: 옛 주소 `findinside.netlify.app`을 새 주소로 넘기지 **않는다**. 두 사이트를 서로 연결하지 않고 각각 자기 주소로 따로 둔다. (이전에 적혀 있던 `_redirects` 리디렉션 계획은 사용자가 안 하기로 해서 지웠다.)

**바뀐 결정(2026-10-10): 검색 엔진용 대표 주소는 netlify.app.** 같은 내용이 두 주소로 색인돼 구글이 한쪽을 숨기고 순위 점수도 나뉘었다(pages.dev `site:` 결과에 "매우 유사한 항목 생략"). 그래서 pages.dev 페이지의 `canonical`·`og:url`·구조화 데이터·`sitemap.xml`·`robots.txt`도 netlify.app을 가리킨다. 방문자 쪽(페이지 링크, 다운로드)은 그대로 각자 주소 — 리디렉션은 여전히 안 한다. 몇 주에 걸쳐 구글 결과에는 netlify.app만 남는다.

저장소의 `site/`는 pages.dev 주소로 되어 있어서 그대로 올리면 Netlify의 sitemap·robots·형식별 안내가 pages.dev를 가리킨다. 그래서 저장소 루트의 `netlify.toml`이 Netlify에게 "`node scripts/site-netlify.js`를 돌린 뒤 `release/site-netlify`를 올려라"라고 알려 준다. 그 스크립트는 `site/`를 복사하면서 주소를 netlify.app으로 바꾼다. Netlify가 저장소를 보고 있으면 푸시할 때마다 저절로 올라간다 (Cloudflare도 같은 푸시로 올라간다).

**끝남(2026-10-09)**: Netlify를 `kimheunghan/Find` 저장소에 연결했고 첫 배포가 17초 만에 Published. 확인 결과 Netlify의 sitemap·robots·형식별 안내가 모두 netlify.app 주소, pages.dev 쪽은 그대로 pages.dev 주소다. 이제 푸시 한 번이면 두 사이트가 각자 주소로 올라간다. (Netlify가 "Pretty URLs" 기능으로 첫 페이지의 `.html` 링크를 `/hwp-search`처럼 바꿔 내보내는데, 정상 동작이고 둘 다 열린다.)

## 2. 스토어 페이지의 "이 버전의 새로운 기능" 글을 1.0.4로 고치기

**스토어 1.0.4는 인증을 통과해 2026-10-08 낮부터 배포 중이다** (스토어 카탈로그에 `FindInside_1.0.4.0_x64`가 올라 있고, 스토어로 설치한 PC는 자동으로 1.0.4가 된다). 그런데 제품 페이지(apps.microsoft.com/detail/9mstc81374sk)의 "이 버전의 새로운 기능" 칸은 1.0.2 때 적은 글 그대로다. 1.0.3·1.0.4 제출 때 이 칸을 안 고쳤기 때문이다.

**스토어 페이지에는 버전이 보이는 자리가 이 칸뿐이다.** 패키지 안의 버전(1.0.4.0)은 설치한 뒤 설정 → 앱과 앱의 정보 창에만 나오고, 올릴 때 파일 이름에 붙인 `_v1.0.4`는 Partner Center에서만 보인다. 그래서 **제출할 때마다 이 칸 첫 줄에 버전을 적는다.**

**할 일 (사용자, 브라우저)**: Partner Center → FindInside → 업데이트 제출 → 스토어 등록 정보(한국어) → "이 버전의 새로운 기능" 칸의 글을 아래로 통째로 바꾸고 제출. **패키지는 건드리지 않는다** (패키지를 올리면 설치한 모든 PC에 업데이트가 간다). 등록 정보만 바꾼 제출도 인증은 거치지만 보통 몇 시간이면 끝나고, 그동안 1.0.4는 그대로 받아진다. 제출 횟수에 제한·비용·불이익은 없다. 단, 인증 중인 제출이 있으면 새 제출을 못 연다.

```
1.0.4 업데이트
- 색인 중에 검색 결과가 몇 초마다 깜빡이던 문제를 고쳤습니다
- 결과 목록이 저절로 맨 위로 튀거나, 누르려던 항목이 바뀌어 다른 메일이 열리던 문제를 고쳤습니다
- 메일 본문의 주소를 누르면 웹브라우저로 열립니다
- 정식 라이선스 키로 활성화할 수 있습니다
```

(1.0.2 글에 숫자만 1.0.4로 바꾸면 안 된다. 그 칸은 "이 버전에서 새로 된 것"을 적는 자리라, 1.0.2 내용에 1.0.4라고 붙이면 틀린 글이 된다.)

스토어 앱 1.0.3은 테스트 상품 번호만 알아서 실제로 산 키를 거절한다. 그래서 Lemon Squeezy 상품 설명·대표 이미지에 안내를 넣어 두었다.

대표 이미지의 황색 띠 문구는 **"MS Store: 업데이트 날짜 2026. 10. 8. 또는 그 이후 판으로 설치"** 다 (2026-10-09에 바꿈). 처음에는 "1.0.3 이하 버전은 라이선스 키 인식 불가"라고 버전으로 적었는데, **스토어 앱 화면에는 버전 번호가 안 보이고 "업데이트 날짜"가 보인다.** 사는 사람이 바로 확인할 수 있는 날짜로 바꿨다 (족보 상품 이미지와 같은 방식).

띠는 `site/product-image.html` 안에 들어 있다. 이미지를 다시 뽑으려면:

```
$env:Path = "C:\Program Files\nodejs;$env:Path"
Remove-Item Env:\ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue   # 없으면 node로 돌아 실패한다
.\node_modules\.bin\electron.cmd scripts/product-image.js release\findinside-product.png
```

**결정(2026-10-10): 띠는 그대로 둔다.** 스토어 판은 옛 버전도 저절로 업데이트되지만, 자동 업데이트를 끈 PC·관리자가 막은 회사 PC·오래 안 켠 PC는 옛 버전에 남아 키가 거절될 수 있어서다. 상품 설명의 "구 버전(1.0.3 이하)… 1.0.4 이상으로 업데이트한 후" 문구도 그대로 둔다.

나중에 지우기로 하면 그 파일의 `.strip` 줄들과 `<div class="strip">` 한 줄만 지우고 `.hero{height:1012px}`를 `1200px`로 되돌린 뒤 다시 뽑으면 띠 없는 이미지가 된다. 뽑은 PNG는 사용자가 Lemon Squeezy 상품 이미지로 올린다.

## 2-1. 설치 파일 링크를 pages.dev 주소로 — 끝남(2026-10-09)

**확인함(2026-10-09)**: 배포 뒤 `findinside.pages.dev/download/Find_Setup_v1.0.4.exe`가 리디렉션 0번으로 200, 112,793,803바이트를 끝까지 받았다. `Find_Setup.exe`도 200, 엉뚱한 이름은 404. 페이지 링크도 pages.dev로 바뀌었다.

설치 파일이 108MB라 GitHub 저장소(100MB 제한)·Cloudflare Pages(파일당 25MB)·Netlify(10MB 넘으면 CDN이 제대로 못 받침)에는 둘 수 없어서 GitHub 릴리스 첨부에 둔다. 예전에는 판매 페이지 링크가 `github.com/.../releases/latest/download/Find_Setup_v<버전>.exe`를 바로 가리켜서, 휴대폰 "다운로드" 목록에 **출처가 github.com**으로 찍히고(족보는 jocbo.pages.dev), GitHub 앱이 깔린 휴대폰에서는 앱이 열렸다.

**고친 방식 (족보와 같음)**: 링크를 `https://findinside.pages.dev/download/Find_Setup_v<버전>.exe`로 바꿨다(`src/product.json`의 `downloadUrl`). 저장소 루트의 `functions/download/[file].js`(Cloudflare Pages 함수)가 그 버전 릴리스(`releases/download/v<버전>/…`)에서 파일을 받아 **그대로 흘려 넘겨준다** — 브라우저는 github.com으로 넘어가지 않으므로 출처가 findinside.pages.dev가 된다. 예전 이름 `Find_Setup.exe`는 latest 릴리스에서 가져온다. 릴리스 올리는 방법은 그대로다.

Netlify 쪽은 사이트마다 따로: `scripts/site-netlify.js`가 링크를 `findinside.netlify.app/download/…`로 바꾸고, `netlify.toml`의 프록시(status 200)가 pages.dev 함수에서 받아 넘겨준다. 그래서 pages.dev에서 받으면 출처가 findinside.pages.dev, netlify.app에서 받으면 findinside.netlify.app이다. (GitHub로 바로 프록시하면 GitHub의 넘김 응답이 브라우저로 가서 출처가 github 쪽이 된다.) 확인(2026-10-09): netlify.app 주소도 리디렉션 0번, 200, 112,793,803바이트, 38초.

주의: Netlify 프록시로 받는 바이트는 Netlify 대역폭(크레딧)으로 센다. 설치 파일 1번에 108MB라 내려받기가 많아지면 크레딧이 빨리 줄 수 있다.

**확인할 것 (푸시 뒤)**: `curl -I https://findinside.pages.dev/download/Find_Setup_v1.0.4.exe`가 리디렉션 없이 `200`·`Content-Length: 1억 남짓`이어야 한다. 404가 나면 Cloudflare Pages 프로젝트 설정의 루트 디렉터리가 저장소 루트인지(그래야 `functions/`를 찾는다) 본다.

## 3. Lemon Squeezy 테스트 상품 내리기 — 공짜 키 막기

1.0.3 앱의 "구매하기"는 테스트 결제 페이지로 간다. 테스트 결제는 시험용 카드 번호로 돈 없이 통과되고 진짜로 작동하는 키가 나온다 (1.0.4도 테스트 상품 번호 1397740을 받는다).
- **Test mode를 켠 상태에서** Products → 「FindInside 라이선스 (PC 2대)」 → ⋯ → **Unpublish** (Delete 말고). 꺼진 상태에서 하면 실제 판매 상품이 내려간다.
- 족보 테스트 상품은 족보 앱을 Live 결제 링크·상품 번호로 바꾼 새 버전이 나간 뒤에 내린다 (먼저 내리면 족보 앱에서 아무도 못 산다).
- 다음 버전에서는 `productId`에서 테스트 번호(1397740)를 빼는 것도 검토한다.
