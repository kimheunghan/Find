# FindInside 제품 요구사항 문서 (PRD)

- 상태: 기획 초안 v1.0
- 대상: Windows 설치형 Local-First 통합 검색·수집 프로그램
- 제품명: FindInside (`Find`는 GitHub 저장소 이름)
- 기준: 이 문서는 FindInside 요구사항의 단일 기준 문서(SSOT)다. 구현 및 검토 시 README보다 본 문서를 우선한다.
- 현재 범위: 기획 문서만 작성하며 앱 소스코드는 작성하지 않았다.

## 1. 제품 정의

FindInside는 Windows PC에 설치하여 로컬 파일, 이메일, 이메일 첨부파일, 저장된 MSG/EML 메일의 제목·경로·메타데이터·내부 내용을 색인하고, 정확 검색과 의미 유사 검색을 결합해 필요한 자료를 찾고 수집하는 Local-First 프로그램이다.

사용자는 정확한 파일명이나 메일 제목을 몰라도 다음과 같은 자연스러운 표현으로 자료를 찾을 수 있어야 한다.

> 서버 IP와 시스템 사양 관련 자료

실제 파일명이 `설치정보.xlsx`이고 메일 제목이 `RE: 자료 전달드립니다`여도 내부에 관련 내용이 있으면 결과에 포함되어야 한다.

## 2. 목표와 비목표

### 2.1 목표

- 흩어진 업무 자료를 하나의 검색창에서 찾는다.
- 파일명뿐 아니라 문서·메일·첨부파일의 내부 내용을 검색한다.
- 정확 검색과 의미 검색을 함께 제공한다.
- 결과가 나온 이유와 관련 위치를 설명한다.
- 검색 후보를 줄이고 사람이 최종 검수하도록 돕는다.
- 검수된 자료를 원본 훼손 없이 수집한다.
- 민감한 회사 자료의 처리를 기본적으로 로컬에서 수행한다.

### 2.2 범위 밖 기능

- v1에 정의하지 않은 파일 형식과 메일 서비스를 임의로 추가하지 않는다.
- AI가 사람 대신 검색 결과를 자동 확정하지 않는다.
- 원본 파일을 기본적으로 이동하거나 삭제하지 않는다.

## 3. 대상 사용자와 대표 사용 사례

### 3.1 대상 사용자

- Windows PC에 업무 자료가 많이 쌓인 개인 사용자
- 문서와 이메일 첨부파일을 자주 다시 찾아야 하는 회사원
- 한국 기업 환경에서 HWP/HWPX를 포함한 다양한 형식을 다루는 사용자
- 외부 클라우드 전송을 최소화해야 하는 조직 사용자

### 3.2 대표 사용 사례

- 정확한 파일명을 모르는 상태에서 내용으로 자료 찾기
- 특정 프로젝트 폴더와 특정 연도의 HWP/XLSX만 검색하기
- 메일 본문 또는 첨부파일 내부에 있는 서버 정보 찾기
- 저장된 MSG/EML의 내부 첨부파일까지 검색하기
- 후보 자료를 검수해 수집함에 넣고 지정 폴더로 복사하기

## 4. v1 지원 범위

### 4.1 문서 및 데이터 파일

- HWP / HWPX
- DOC / DOCX
- XLS / XLSX
- PPT / PPTX
- PDF
- TXT / CSV

한국 회사 환경을 고려해 HWP/HWPX 지원은 필수다.

### 4.2 메일

- Microsoft 365 / Outlook: Microsoft Graph API + OAuth
- 일반 회사메일: 범용 IMAP
- 로컬 저장 메일: MSG / EML

범용 IMAP은 특정 업체에 종속되지 않아야 하며 사용자가 다음 값을 직접 설정할 수 있어야 한다.

- IMAP 서버
- 포트
- 보안 방식: SSL/TLS, STARTTLS, 없음
- 계정
- 인증정보

포트 993 등 특정 값을 하드코딩하지 않는다. Mailplug는 범용 IMAP의 사용 사례일 뿐 별도 전용 연동으로 정의하지 않는다.

메일 검색 대상은 다음과 같다.

- 제목, 본문
- 발신자, 수신자, 참조
- 날짜
- 첨부파일명
- 첨부파일 내부 내용

MSG/EML도 본문만이 아니라 내부 첨부파일까지 분석한다.

## 5. 통합 검색

하나의 검색창에서 다음 대상을 동시에 검색한다.

- 파일명, 폴더명, 전체 경로
- 문서 내부 내용
- 메일 제목, 본문, 헤더
- 메일 첨부파일명과 내부 내용
- MSG/EML 내용과 내부 첨부파일
- 의미적으로 유사한 내용

### 5.1 검색 방식

- IP 주소, 고유번호, 정확한 문구는 정확 검색을 우선한다.
- `서버 구축 관련 자료` 같은 개념 질의에는 의미 검색을 적극 활용한다.
- 두 방식의 결과를 결합하되 검색 근거를 사용자에게 설명한다.

### 5.2 검색어 조합

- 여러 단어를 조합한 일반 검색
- `AND`, `OR`, `NOT`
- 따옴표를 이용한 구문 검색(예: `"운영 서버"`)
- 고급 문법을 모르는 사용자를 위한 조건 추가 UI

### 5.3 검색 범위와 필터

- 전체
- C:, D: 등 드라이브
- Documents, Downloads, Desktop
- 카카오톡 다운로드 폴더
- 사용자 지정 폴더
- 파일 형식
- 날짜/기간
- 메일 관련 조건

색인 범위와 검색 범위는 구분한다. 색인 범위는 평소 분석해 둘 자료의 범위이고, 검색 범위는 이미 색인된 자료 중 이번 검색에서 확인할 범위다.

### 5.4 결과 내 재검색

사용자는 기존 결과에 검색어와 필터를 단계적으로 추가하거나 제거할 수 있어야 한다. 화면에서는 조건 칩을 제공한다.

예: `[서버 ×] [IP ×] [운영 ×] [D:\\업무 ×] [HWP ×] [XLSX ×]`

## 6. 색인

### 6.1 초기 설정

첫 실행 시 색인할 위치를 선택한다.

- Documents, Downloads, Desktop 등 기본 후보
- 사용자 지정 폴더 추가
- 제외 폴더 설정
- Windows 및 Program Files 같은 시스템 폴더는 기본 선택하지 않음

### 6.2 증분 색인

- 첫 실행: 선택 범위 전체 분석
- 이후: 신규, 수정, 삭제된 항목만 반영
- 전체를 매번 재분석하지 않는다.

### 6.3 내부 위치 정보

가능한 범위에서 결과와 함께 다음 위치를 저장하고 표시한다.

- Excel: 시트명, 관련 셀
- PDF: 페이지
- PowerPoint: 슬라이드 번호
- HWP/Word: 관련 문단 또는 표

## 7. 검색 결과와 설명 가능성

각 결과에 다음 정보를 표시한다.

- 파일 또는 메일의 기본 정보
- 관련도
- 일치한 내용의 미리보기
- 내부 위치
- 검색된 이유

검색 근거 예시:

- 내부에 IP 주소 존재
- `WEB SERVER` 발견
- CPU / MEMORY 항목 존재
- `서버 사양`과 의미적으로 관련

관련도 숫자만 제시하는 검은상자 방식은 피한다.

## 8. 육안 검수

각 결과에 다음 상태를 제공한다.

- 관련 있음
- 관련 없음
- 보류

시스템은 대량 자료를 소수 후보로 좁히고, 최종 정답 선택은 사람이 수행한다. 검수 결과는 향후 검색 품질 개선에 활용할 수 있으나 사용자의 명시적 선택을 임의로 덮어쓰지 않는다.

## 9. 수집함

검수한 자료를 수집함에 추가할 수 있다.

1. 논리적 수집: 원본 위치와 참조만 기록
2. 실제 수집: 사용자가 지정한 폴더로 파일 복사

원본은 기본적으로 이동하거나 삭제하지 않는다. 파일 복사 시 충돌, 실패, 권한 부족을 명확히 안내해야 한다.

## 10. Local-First 및 보안 원칙

- 문서 분석, 검색 DB, 키워드 검색과 가능한 의미 검색은 기본적으로 PC 내부에서 처리한다.
- 계약서, 고객자료, 서버 IP 등 민감한 내용을 기본 구조에서 외부 AI로 전송하지 않는다.
- 외부 연동이 필요한 경우 범위와 목적을 명확히 알리고 사용자 동의를 받는다.
- 메일 인증정보와 토큰은 안전하게 보관하며 평문 저장을 피한다.
- 로그에 문서 원문이나 인증정보를 불필요하게 남기지 않는다.

## 11. 배포 및 플랫폼

### 11.1 Windows

- 목표 배포 파일: `Find_Setup.exe`
- 사용자가 Python, Node.js 등 별도 런타임을 설치하지 않아도 된다.
- 설치, 초기 색인, 업데이트, 제거 흐름을 제공한다.

### 11.2 모바일(후속)

- Android: APK / AAB
- iOS 앱
- 모바일이 PC 디스크 전체를 직접 색인하지 않는다.
- Windows Find의 검색 엔진·인덱스와 연동해 검색, 결과 확인, 검수, 수집함 확인을 수행한다.

## 14. 제품 관계와 설계 기준

Everything은 파일명과 경로를 알고 있을 때 빠르게 찾는 도구이고, Find는 파일명을 몰라도 내부 내용과 의미로 찾는 도구다. 두 제품은 경쟁 대체 관계로만 정의하지 않으며 함께 사용할 수 있다.

구현 과정에서 새로운 기능이나 해석이 필요하면 먼저 이 PRD를 변경하고 합의한 뒤 구현한다. PRD에 없는 기능을 임의로 앱 범위에 추가하지 않는다.
